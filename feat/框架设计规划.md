# Vike-CF 框架设计规划

> **文档状态：2026-08-07 已依据当前源码核查。**
>
> 本项目是个人商城，不建设多角色 RBAC、审计平台或为未来预留的后台 REST API；但必须建设统一全局错误处理，并将完整接口与异常信息输出到 Cloudflare Workers Observability。后续改造以第 8 节进度表为准。

## 1. 项目模型与接口边界

`vike-cf` 使用 Vike + Vue + Hono + Cloudflare Workers：

- Vike 页面与 `+data.server.ts` 负责 SSR；
- Vue 页面与本项目服务端的业务交互优先使用 Telefunc，传输端点固定为 `/_telefunc`；
- Hono 仅处理 Better Auth、支付回调，以及未来确有外部调用需求的 HTTP API；
- D1 + Drizzle 负责持久化。

### 1.1 不为后台重复建设 Ajax API

后台 Vue 页面不建设传统 `/admin/*` 或 `/${ADMIN_PATH}/api/*` Ajax API：

1. 页面直接导入 Telefunc `on*` 函数，避免同一业务维护两套 DTO、错误处理和权限判断；
2. Telefunc 的共享传输路径为 `/_telefunc`，不位于 `ADMIN_PATH` 下；URL 前缀不是权限依据；
3. 当前没有公开业务 REST API、管理 REST API 或 `apiClient`，没有真实需求时不预留空接口。

接口按调用方和协议划分：

| 类别 | 当前入口 | 用途 | 返回与权限 |
| --- | --- | --- | --- |
| SSR 服务调用 | `+data.server.ts` -> `server/<domain>` | 首屏公开数据、受后台页面 guard 保护的数据 | 不经 HTTP/Telefunc；调用点确认数据访问范围 |
| 页面业务 RPC | Telefunc `on*` -> `/_telefunc` | 公开页、用户能力与后台交互 | 成功直接返回业务数据；入口验证输入和权限 |
| Better Auth | `/api/auth/**` | 注册、登录、会话 | 遵从 Better Auth 协议 |
| 支付回调 | `/api/payments/alipay/notify` | 支付宝服务端通知 | 验签、金额与订单校验；返回协议要求的 `success` / `failure` |
| 外部 HTTP API | `/api/*` | 仅第三方或外部客户端确有需求时 | HTTP 状态 + `{ code, message, data }`；按业务验证凭证或签名 |

“公开 HTTP API”只表示可被站外调用，不等于匿名。当前订单查询、创建订单和发起支付均使用 Telefunc。

## 2. 最小权限模型

项目只使用三个简单角色，不引入角色表、权限点、策略引擎或多管理员授权设计：

| 角色 | 含义 | 当前来源 | 可访问能力 |
| --- | --- | --- | --- |
| `guest` | 未登录访客 | 无会话 | 公开页面、guest 下单、订单号与下单邮箱查询、邮箱验证码恢复 guest 订单 |
| `user` | 已登录普通用户 | Better Auth 会话 | 账户下单、本人订单、地址簿与账户资料 |
| `root` | 唯一管理员 | `adminBootstrap(id=1)` 指向的用户 | `ADMIN_PATH` 后台页面与所有管理 Telefunc |

### 2.1 Root 规则

- 项目只有一个 `root`；不提供后台创建、启用、停用、切换多个管理员的功能。
- `adminBootstrap(id=1).userId` 指向的唯一用户是 `root`；其他已登录账号一律视为 `user`。
- 删除“第一个成功的邮箱密码注册用户成为管理员”的逻辑。Root 只能通过受部署初始化授权保护的一次性 `/setup` 创建；初始化完成后 `/setup` 统一返回 404。
- 后续不做复杂恢复、审批或管理员审计流程。若需要更换 root，由站长通过受控数据库维护 `adminBootstrap(id=1).userId`，并始终只保留一名 root。

### 2.2 服务端授权

客户端隐藏菜单、禁用按钮和 `ADMIN_PATH` 都不是权限判断。服务端入口必须按如下最小规则处理：

- 公开能力：只返回公开字段；guest 单笔订单查询同时匹配不可枚举的订单号与标准化下单邮箱，失败时不区分订单不存在或条件错误；
- 用户能力：使用 `requireUser()`，并在需要时验证资源属于当前用户；
- 管理能力：使用 `requireAdmin()`，它代表 `root`；
- 支付回调：仅相信验签后的数据，并核对应用 ID、订单、金额和状态。

所有管理 Telefunc 都应统一调用 `requireAdmin()`。当前部分模块仍有私有 `getAdminDb()` / `getAdminContext()`；后续迁移到统一 helper，目标只是让 `AUTH_REQUIRED`、`ADMIN_ACCESS_REQUIRED`、`DATABASE_UNAVAILABLE` 的行为一致，不增加额外权限体系。

## 3. `ADMIN_PATH` 后台访问

### 3.1 页面路径

`ADMIN_PATH` 是 Worker 环境变量：

```text
pages/@adminPath/              -> /${ADMIN_PATH}            （后台登录）
pages/@adminPath/dash/         -> /${ADMIN_PATH}/dash
pages/@adminPath/catalog/.../  -> /${ADMIN_PATH}/catalog/...
```

`pages/@adminPath/+guard.server.ts` 必须保持：

1. 路由参数必须与 `env.ADMIN_PATH` 完全一致，否则返回 404；
2. 仅 `/${ADMIN_PATH}` 可作为后台登录页匿名访问；
3. 其他 `pages/@adminPath/**` 页面要求已登录且为 root；
4. 新后台页只能放在 `pages/@adminPath/**`，不能建根级别别名或兼容跳转。

`ADMIN_PATH` 使用随机、不可预测的单段路径名；不得出现在公开页面数据、导航、客户端环境变量、错误提示或普通日志中。公开商城即使识别到当前账户是 root，也必须按普通 user 展示，不能显示后台入口或 root 标记。它用于减少扫描，不代替 root 验证。

管理员初始化固定使用独立的 `/setup`，但该页面不得展示、返回或跳转到 `ADMIN_PATH`。`/setup` 仅在系统尚无 root 且请求通过独立部署初始化授权时可创建 root，不能采用“谁先访问谁成为 root”；完成后永久关闭并返回 404。公开 `/signup` 在 root 尚未初始化时不允许注册，只显示“网站还未初始化，请稍后再试...”，初始化完成后只能创建普通 `user`。

### 3.2 Telefunc 与后台接口

“`ADMIN_PATH` 目录下的页面与接口只允许管理员访问”在 Vike 中的准确实现是：

- `pages/@adminPath/**` 由目录 guard 限制为 root；
- 管理 Telefunc 虽通过共享 `/_telefunc` 访问，但每个函数都调用 `requireAdmin()`；
- 只有未来出现 Telefunc 不能覆盖的外部管理工具需求时，才创建 `/${ADMIN_PATH}/api/*`，并在 Hono 中校验当前会话为 root。

当前没有管理 HTTP API，不为它提前增加 middleware 或目录。

## 4. 错误处理与日志脱敏

### 4.1 前端错误必须脱敏

前端只显示 `lib/error-messages.ts` 中的固定中文文案。不得向用户展示 `Error.message`、数据库错误、SQL、堆栈、第三方响应、支付参数、密钥、Cookie、令牌或卡密。

- 预期业务失败使用稳定的 `UPPER_SNAKE_CASE` 错误码，例如 `AUTH_REQUIRED`、`ADMIN_ACCESS_REQUIRED`、`PRODUCT_NOT_FOUND`；新增错误码同步加入 `lib/error-messages.ts`。
- 未知错误、网络错误和服务端 500 统一显示：`接口异常，请稍后重试。`。
- 有短暂反馈的 Telefunc 通过 `runTelefunc()` 调用；它负责显示一次 Toast，调用方只处理 loading/saving 状态。
- 读取失败或表单校验确实需要持续展示时，可用 `runTelefunc(..., { notifyError: false })` 后在本地 Alert 显示映射文案；同一错误不能同时 Toast 与 Alert。
- Better Auth 的登录、注册错误同样映射为固定文案，不能直接使用 `res.error.message` 或捕获到的 `cause.message`。

Telefunc 成功时直接返回数据，不套 `{ code, message, data }`。未来 HTTP API 才使用该 JSON 信封；支付回调继续使用提供方要求的纯文本协议。

### 4.2 全局错误处理与三层信息策略

所有未预期异常必须经过同一个服务端错误处理入口。该入口覆盖三条请求链路：

1. Hono HTTP 路由（包括支付回调的异常分支）；
2. Telefunc `/_telefunc`；
3. Vike SSR、`+data.server.ts` 与页面 guard。

统一入口负责区分预期业务错误与未预期异常，并同时完成三种输出：

| 输出位置 | 信息策略 | 目的 |
| --- | --- | --- |
| 前端响应与页面提示 | **脱敏**：稳定错误码和固定中文文案 | 不向用户泄露内部实现和敏感数据 |
| 数据库支付、邮件、推送业务日志 | **仅脱敏** `sign`、密码、token、API key、Secret、私钥和 access key | 保留个人商城后台排查所需的完整业务上下文 |
| Cloudflare Workers Observability | **不脱敏**：完整请求接口信息、请求参数、原始异常、堆栈和第三方响应 | 供 root 在 Cloudflare 控制台定位真实故障 |

Observability 的完整记录是明确需求，因此全局错误处理不得先修改异常对象或请求数据再输出到 Workers 日志。该信息只能通过 Cloudflare 账号权限查看，不能写回数据库、响应给前端或复制到后台页面。

实现约定：

- 预期业务错误（`AppError` / 稳定错误码）直接转为前端映射文案；可按需要记录简要信息，但不必作为未预期异常上报。
- 未预期异常先向 Workers Observability 输出原始 `Error`、完整接口路径、方法、查询参数、请求体/表单参数和可用的请求上下文，再返回统一的 `INTERNAL_ERROR` 脱敏文案。
- HTTP API 返回 `{ code, message, data }`；Telefunc 保持抛出语义，由客户端 `runTelefunc()` 处理；支付回调继续返回协议要求的 `failure`，但异常仍进入 Observability。
- 认证页不直接显示 Better Auth 原始错误；其原始错误由全局错误处理输出到 Observability，页面只显示固定文案。

数据库业务日志继续按当前业务需要保存，用于后台排查；最小脱敏规则为：

1. **支付回调：** 保存回调业务字段时移除 `sign`；不得保存支付私钥、应用密钥或其他 secret 值。
2. **邮件/推送：** 可以保存收件人、主题、状态和错误信息；不得保存 Provider 配置中的密码、token、API key、Secret 或完整授权头。
3. **配置与异常：** 不把 Worker Secret、支付私钥、S3 access key/secret、邮件 token 或机器人 token 写入数据库日志或返回前端。
4. **管理员操作：** 不建设审计系统；现有 `adminOperationLog` 在唯一 root 改造中移除，不再新增审计页面、记录、报表或相关权限设计。

## 5. 后台信息架构、URL 与目录

`lib/admin-navigation.ts` 是后台页面元数据、路径和层级数据的唯一来源：`adminPages` 提供 `title`、`path`、`pageTitle`、`description`，`adminNavigation` 提供分组和模块层级。侧栏链接、面包屑、模块内导航和页面标题必须引用它们，不得维护第二套路由表。

后台最多三级：**一级业务分组 -> 二级页面/模块 -> 三级模块内页面**。另允许独立页面；一级分组不生成同名 URL，三级页不得并列为二级菜单或创建平行入口。页面目录与省略 `ADMIN_PATH` 后的正式 URL 必须一一对应。

| 类型/分组 | 正式路径（省略 `/${ADMIN_PATH}`） | 页面目录 | 页面 |
| --- | --- | --- | --- |
| 独立页面 | `/dash` | `pages/@adminPath/dash` | 面板 |
| 商品管理 | `/catalog/*` | `pages/@adminPath/catalog` | 分类、商品、卡密、折扣码 |
| 独立页面 | `/orders` | `pages/@adminPath/orders` | 订单管理 |
| 推送管理 | `/push/*` | `pages/@adminPath/push` | 推送配置、发送日志、电子邮件；邮件下含通道配置、模板 |
| 系统配置 | `/system/*` | `pages/@adminPath/system` | 支付渠道、媒体存储、站点配置、安全配置、任务 |
| 用户管理 | — | — | 当前不提供用户或管理员管理页面 |

邮件模块唯一二级入口是 `/push/email`，三级页只能为 `/push/email/post-office`、`/push/email/templates` 等同前缀路径；不得新增 `/mail/*`、`/notifications/*`、`/push/email/overview` 或兼容路径。

新增或移动后台页时：

1. 在 `adminPages` 注册完整元数据；
2. 加入既有 `adminNavigation` 分组或模块；
3. 在 `pages/@adminPath` 创建与 `path` 对应的 `+Page.vue`；
4. 使用 `AdminPageHeader` 或模块布局读取集中元数据；
5. 更新链接并删除旧路径，不保留别名。

详细页面、列表与导航约定见 [dev.md](./dev.md)。

## 6. 分层与共用组件

| 目录 | 职责 |
| --- | --- |
| `pages/` | 路由页面、页面组合、查询状态、用户交互 |
| `components/ui/` | shadcn-vue 基础组件与通用封装 |
| `components/admin/` | 跨后台页展示与交互基座 |
| `components/` | 跨页面组合组件，如侧栏、支付二维码 |
| `lib/` | 无 I/O 的类型、错误映射、导航、格式化、校验与客户端调用封装 |
| `server/<domain>/` | 按领域组织 Telefunc、服务逻辑和协议适配 |
| `database/` | schema、migration 与 Drizzle 基础设施 |

- 优先复用 `components/ui`、`components/admin` 与 `components`；缺少能力先确认 shadcn-vue，再封装为可复用组件。
- 业务页面不得用原生 `input`、`select`、`textarea`、`button` 绕开统一组件。
- 后台实体管理列表使用 `AdminDataTable`；仪表盘摘要表可以使用基础 `Table`。
- `AdminDataTable` 默认显示操作列，无行操作时传 `:show-actions="false"`。
- 短暂反馈使用 Sonner Toast；不可恢复操作使用 `DialogRoot` 确认，服务端仍验证状态和 root 权限。
- 仅一个页面使用的小组件可就近放置；跨模块复用时提升到共享目录，并更新 [components.md](./components.md)。
- JSON 配置映射表单统一遵循 [json表单.md](./json表单.md)；后续支付、邮件、存储等 Provider 配置页面必须复用该定义驱动的表单抽象，不重复实现字段渲染、类型转换和 Secret 处理。
